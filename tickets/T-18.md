## T-18: Implement SessionRepository on SQLite with versioned migrations
**Fase:** F4  **Depende de:** T-17c · **ADR:** 001 (SQLite), 004 (sin secretos en SQLite)
**Contexto:** Persistencia de sesiones y carpetas. El plan permite `sqlx` o `rusqlite`: se usa **`rusqlite` con `bundled`** (sin SQLite del sistema, compila igual en los 3 SO) detrás de `spawn_blocking`. Migraciones versionadas con `PRAGMA user_version` y SQL embebido (sin crate extra). **Ningún secreto** en la base: el esquema no tiene columnas para contraseña ni passphrase.

**Archivos a crear/modificar:**
- `crates/adapters/Cargo.toml` (modificar: `rusqlite = { version = "0.37", features = ["bundled"] }` o la última estable compatible con MSRV 1.100)

- `crates/adapters/src/session_repository.rs` (crear: `SqliteSessionRepository` + migraciones + tests unitarios con SQLite en memoria)
(+ `Cargo.lock`)

**Esquema v1:**
- `folders(id INTEGER PRIMARY KEY, name TEXT NOT NULL, parent INTEGER NULL REFERENCES folders(id) ON DELETE CASCADE)`
- `sessions(id INTEGER PRIMARY KEY, name TEXT NOT NULL, hostname TEXT NOT NULL, port INTEGER NOT NULL CHECK(port BETWEEN 1 AND 65535), username TEXT NOT NULL, auth_kind TEXT NOT NULL CHECK(auth_kind IN ('password','key')), remember_password INTEGER NOT NULL DEFAULT 0, key_path TEXT NULL, key_has_passphrase INTEGER NOT NULL DEFAULT 0, folder INTEGER NULL REFERENCES folders(id) ON DELETE SET NULL)`
- `PRAGMA foreign_keys = ON` en cada conexión.

**Reglas:**
- Todas las operaciones dentro de `tokio::task::spawn_blocking`; el `Mutex` es `std` y solo vive dentro del closure bloqueante. Mutex envenenado → `RepositoryError::Io`; sin `unwrap`/`expect`.
- Los IDs se generan con `next_*_id` = `MAX(id)+1` (1 si está vacía). `save_*` es upsert (`INSERT ... ON CONFLICT(id) DO UPDATE`).
- Al leer, las filas se reconstruyen con los constructores del dominio (`Hostname::new`, `Port::new`, `Session::new`, `KeyRef::new`, …); una fila inválida → `RepositoryError::Io` (nunca `panic!`).
- `delete_session`/`delete_folder` de un id inexistente → `NotFound`. Carpeta `parent` o sesión `folder` apuntando a una carpeta inexistente → `Conflict` (violación de FK).
- Borrar una carpeta borra sus subcarpetas (CASCADE) y deja sus sesiones en la raíz (`SET NULL`).
- Los errores de `rusqlite` se mapean sin incluir SQL ni valores.

**Criterios de aceptación (unit con `in_memory()` + `#[tokio::test]`):**
- [ ] CRUD de sesión con contraseña y con llave: `save` → `get` devuelve la misma `Session`; `save` con el mismo id actualiza (puerto, usuario, método de auth); `list_sessions` las devuelve ordenadas por id; `delete` → `get` = `None`.
- [ ] CRUD de carpetas, incluida jerarquía; borrar carpeta padre borra hijas y deja sesiones con `folder = None`.
- [ ] `next_session_id`/`next_folder_id`: 1 en vacío; `max + 1` después.
- [ ] Borrar inexistente → `NotFound`; carpeta inexistente como `folder`/`parent` → `Conflict`.
- [ ] Migraciones: abrir dos veces el mismo archivo (tempfile) no falla y conserva los datos; `user_version` = `MIGRATIONS.len()`.
- [ ] Fila corrupta insertada a mano (puerto 0 no pasa el CHECK; usar `hostname = ''`) → `list_sessions` devuelve `Err(Io)` sin panic.
- [ ] El esquema no tiene columnas `password`/`passphrase` (test sobre `PRAGMA table_info(sessions)`).
- [ ] `just check` en verde (incluye `cargo deny`/`audit` con la nueva dependencia).
