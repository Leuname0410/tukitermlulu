## T-22c: Run the transfer queue in desktop and expose transfer commands and progress events
**Fase:** F5  **Depende de:** T-22b
**Contexto:** Composition root de las transferencias. Un único worker Tokio saca trabajos de `TransferQueue` (T-22b), uno a la vez, y llama a `FileTransfer` (T-22a, `RusshFileSystem`). La UI recibe el estado de la cola por un evento Tauri **limitado** (como mucho 10 por segundo por trabajo, más los cambios de estado), nunca bytes de archivo.

**Archivos a crear/modificar:**
- `crates/desktop/src/transfers.rs` (crear: worker, DTOs, comandos, `TransferProgress` que actualiza la cola)
- `crates/desktop/src/terminal.rs` (modificar: `AppState` gana `fs: RusshFileSystem` y `transfers: Arc<std::sync::Mutex<TransferQueue>>` + `Notify`; `disconnect` llama a `cancel_connection`)
- `crates/desktop/src/main.rs` (modificar: crear el worker en `setup` con `tauri::async_runtime::spawn` y registrar comandos)
- `ui/src/lib/api.ts` (modificar: wrappers + `onTransfers(listener)`)
- `ui/src/lib/api.test.ts` (modificar)

**Interfaces / firmas esperadas:**
```rust
#[derive(Serialize, Clone)] #[serde(rename_all = "camelCase")]
pub struct TransferDto { id: u64, connection_id: u64, direction: &'static str /* "download" | "upload" */, remote: String, local: String,
    state: &'static str /* queued|running|done|failed|cancelled */, transferred: u64, total: Option<u64>, error: Option<String> }
#[tauri::command] async fn enqueue_download(state, app, connection_id: u64, remote: String, local_dir: String) -> Result<u64, CommandError>;   // local = local_download_target(dir, remote)
#[tauri::command] async fn enqueue_upload(state, app, connection_id: u64, local_path: String, remote_dir: String) -> Result<u64, CommandError>; // remote = RemotePath(remote_dir).join(nombre local); nombre inválido → invalid_input
#[tauri::command] fn cancel_transfer(state, app, id: u64) -> Result<(), CommandError>;      // id desconocido → not_found
#[tauri::command] fn clear_transfers(state, app);
#[tauri::command] fn list_transfers(state) -> Vec<TransferDto>;
// evento "transfers" con Vec<TransferDto> tras cada cambio de estado y en progreso limitado
```
**Reglas:**
- El `Mutex` de la cola es `std` y **nunca** se mantiene a través de un `.await`. El worker: `lock → start_next → unlock → await transfer → lock → finish → unlock → emit`, y espera en el `Notify` si no hay trabajo.
- `local_dir` debe existir y ser un directorio (si no → `invalid_input`); `local_path` debe ser un archivo.
- `TransferError` → `CommandError`/`error` con su mensaje literal (sin rutas).
- Sin `unwrap`/`expect` en producción. Los errores al emitir eventos se ignoran.

**`api.ts`:** `enqueueDownload(connectionId, remote, localDir)`, `enqueueUpload(connectionId, localPath, remoteDir)`, `cancelTransfer(id)`, `clearTransfers()`, `listTransfers()`, `onTransfers(listener: (jobs: TransferDto[]) => void): Promise<() => void>` (usa `listen` de `@tauri-apps/api/event`; valida la carga útil sin `any`).

**Criterios de aceptación:**
- [ ] Rust unit: `TransferDto` desde cada `TransferState`; el `Throttle` (función pura `should_emit(last: Instant, now: Instant) -> bool` con 100 ms) emite el primero y limita los siguientes.
- [ ] Rust unit: `enqueue_upload` con un nombre local que `RemotePath::join` rechace → `invalid_input`; `local_dir` inexistente → `invalid_input` (funciones de validación extraídas y testeadas sin Tauri).
- [ ] Rust integración (`desktop` no tiene acceso al contenedor; usa un `FileTransfer` mock): el worker procesa 2 trabajos en orden, uno a la vez; `cancel` de un `Running` termina en `cancelled`.
- [ ] UI: cada wrapper invoca su comando con argumentos camelCase; `onTransfers` descarta cargas mal formadas.
- [ ] `just check` y `just test-int` en verde.
