## T-32a: Automated network KPI benchmarks with regression gate
**Fase:** F7  **Depende de:** T-33c · **Decisión:** D4 (mediana de 5, umbral del 20 %, solo en PR a `main` y en tags)
**Contexto:** Medimos contra el contenedor de pruebas los KPIs que no necesitan GUI:
- **tiempo de conexión** (TCP + handshake + auth con llave Ed25519);
- **latencia de tecla a eco**, p95: escribir 1 byte en el PTY de `cat` y medir hasta recibirlo;
- **throughput SFTP**: descarga de 64 MiB comparada con el cliente `sftp` de OpenSSH, como ratio.

El tamaño del instalador ya se midió en T-33a (4.49 MB); el arranque en frío y la RAM van con la GUI (T-31a).

**Archivos a crear/modificar:**
- `crates/adapters/tests/kpi.rs` (crear: `#![cfg(feature = "integration")]`; un único test `#[ignore]` llamado `kpi_benchmarks`, para que `just test-int` no lo ejecute)
- `docs/kpi-baseline.json` (crear)
- `justfile` (modificar: receta `kpi`)
- `.github/workflows/ci.yml` (modificar: job `kpi`)
- `tests/fixtures/Dockerfile` (modificar solo si hace falta `cat`, o un archivo de 64 MiB generado al arrancar; preferible generarlo en el test vía `exec`: `head -c 67108864 /dev/urandom > /tmp/kpi.bin`)

**Reglas:**
- Cada KPI se mide 5 veces y se usa la **mediana**. Para la latencia, cada repetición es el p95 de 200 pulsaciones.
- La sesión se reutiliza con los helpers ya existentes en `crates/adapters/tests/` (puerto 2222, usuario `tuki`, llave `tests/fixtures/ed25519`). Si no hay helper compartido, se copia lo mínimo.
- OpenSSH de referencia: `sftp -b - -i tests/fixtures/ed25519 -P 2222 -o StrictHostKeyChecking=no -o UserKnownHostsFile=<null> tuki@127.0.0.1` con `get /tmp/kpi.bin <tmp>`, cronometrado con `std::process::Command`. Si `sftp` no está en el PATH, el ratio se marca como `skipped` sin fallar (Windows local).
- `docs/kpi-baseline.json`:
  - formato `{ "targets": {"connect_ms": 1500, "echo_p95_ms": 16, "sftp_ratio": 0.8}, "baseline": {"connect_ms": null, "echo_p95_ms": null, "sftp_ratio": null} }`;
  - con `serde_json`, que ya está en las dev-dependencies (si no, añadirlo a `[dev-dependencies]` de adapters).
- Falla el test si:
  - (a) un KPI incumple su `target`;
  - (b) hay `baseline` no nulo y el KPI empeora más del 20 % (mayor para `_ms`, menor para `ratio`).
- Salida:
  - una tabla Markdown (KPI | mediana | target | baseline | estado) por stdout;
  - si existe `GITHUB_STEP_SUMMARY`, se añade a ese archivo;
  - si existe `KPI_WRITE_BASELINE=1`, reescribe `baseline` con las medianas, para que el humano lo commitee.
- `justfile`: `kpi:` levanta el contenedor como `test-int` y ejecuta `cargo test -p tuki-adapters --features integration --test kpi -- --ignored --nocapture --test-threads=1`.
- `ci.yml`, job `kpi`:
  - `runs-on: ubuntu-latest`;
  - `if: github.event_name == 'pull_request' || startsWith(github.ref, 'refs/tags/')`;
  - pasos: checkout, toolchain, cache, `taiki-e/install-action` con `just` y `just kpi`;
  - el job `check` no se toca.
- Funciones de cálculo puras (`median`, `p95`, `evaluate(kpi, value, target, baseline) -> Status`) con tests unitarios **no ignorados** en el mismo archivo, que corren con `just test-int`.

**Criterios de aceptación:**
- [ ] Tests unitarios:
  - `median` de 5 valores;
  - `p95` de 200 valores;
  - `evaluate`: target incumplido → falla; empeora un 21 % sobre baseline → falla; un 19 % → pasa; `sftp_ratio` con baseline 1.0 y valor 0.79 → falla por baseline.
- [ ] `just kpi` en local (Windows con Docker) produce la tabla. El ratio de SFTP puede salir `skipped`.
- [ ] `just check` y `just test-int` en verde; `kpi_benchmarks` no corre en `test-int`.
- [ ] YAML de `ci.yml` válido.

**Commits:** `test(adapters): kpi math and regression rules [T-32a]` → `feat(ci): automated network kpi benchmarks [T-32a]`

**Fuera de alcance:** KPIs con GUI (T-31a), cobertura (T-32b), benchmarks en macOS y Windows.
